Data privacy findings (item 9)
These were checked before any key exists, deliberately: these are photographs of identifiable schoolchildren.

Mathpix — retention is opt-in by default, and we opt out.

improve_mathpix defaults to true. In that state Mathpix retains the image up to 90 days, caches the result for 30, makes the request queryable via /v3/ocr-results, and routes processed images into an internal QA database.
Every request we send carries metadata: {"improve_mathpix": false} (ocr.ImproveMathpix = false). Mathpix documents that in this state the image is not written to disk, the result not cached, the request not queryable — only billing/audit metadata remains.
⚠️ Mathpix's own pages disagree: the Data Retention page says 90 days, the Snip privacy page says 60. Not resolved — if a fixed number matters to the school's policy, confirm it with them before enabling a key.
Mathpix also exposes retention per API key. Confirm the key-level setting is off too when one is purchased.
Because the opt-out is load-bearing, TestMathpixDisablesImprovementOptOut fails if the flag is flipped, removed, or left absent.
Google Cloud Vision — no training on submitted content. Google states it doesn't use submitted content except to provide the service, doesn't use it to train or improve the models, doesn't claim ownership. Online BatchAnnotateImages (what we call) processes in memory, not persisted. Processing region defaults to global and is a project-level setting — constrain it deliberately if the school has a residency requirement; this code does not control it.

Verdict: as configured, neither retains nor trains on student images. For Google that's their standing default; for Mathpix it holds only because we explicitly opt out of a default that would otherwise do exactly that.

Known issues flagged
(a) Image size is the most likely real-world failure. Mathpix caps src at 2MB base64 (mathpixMaxBase64Bytes, checked locally in mathpix.go:109 so you get a clean error instead of a mystery 400). The OCR queue picks via image_picker at maxWidth: 2200, imageQuality: 92 — that lands around 1.75–3.3MB once base64-encoded depending on page detail. Borderline to over. Separately, Phase 3's crop pipeline encodes lossless PNG (page_codec.dart), which will comfortably exceed the cap — that only bites when Phase 5 routes those pages here. Needs a downscale/down-encode decision with a real photo.

(b) Nothing persists a reading on the server. The generate response is the only delivery. If it's lost in transit, a retry hits the server's "already generated" 409 and the reading is unrecoverable — the client reports it honestly and asks the teacher to resubmit rather than showing an empty reading as real. ocr_result (above) fixes this; scan_pages is the Phase 5 home.

(c) aiPublish does not validate drafts (questions.go:330) — publishes whatever exists. Pre-existing, unchanged by me.

(d) The client's own draftFor template simulation still exists (question_gen_repository.dart:52) for the offline path. Untouched — it will now disagree with what the server produces. Needs deciding in Phase 5/6.
